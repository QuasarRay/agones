Keep syntax/import/expansion checks focused on adopted patterns and rerun only affected evidence. Template-generated properties still follow D1's gate and preserve independent invariants.

For each library, record its meaningful use sites, repeated work removed or avoided, validation, and a short contributor example in existing documentation/state. Unused dependencies or toy demonstrations do not establish adoption. A missing use or incompatibility remains an explicit deferred/blocked adoption item with a concrete revisit trigger; it cannot silently remove a named library from the contract. Continue other feature work rather than building a speculative integration framework or forcing a harmful use merely to check a box.

**C8 — Python-familiar readability with idiomatic Rust semantics.** Make common code read as small, well-named functions, clear data transformations/comprehensions, reusable templates, and compact CGP composition. Keep public APIs typed and conventional: structs/enums, traits/generics, explicit ownership/borrowing, `Option`/`Result`, normal error propagation, and source-compatible async/cancellation behavior. Preserve Rust's safety and performance model; do not add a Python interpreter, dynamic object layer, or unnecessary cloning, boxing, allocation, or runtime dispatch just to imitate Python syntax.

Select comprehensions where they clarify mapping/filtering/collection construction. Keep complex effects, resource ownership, retries, and lifecycle control explicit in CGP providers. Use an ordinary loop or iterator when it is clearer or semantically necessary, recording a local reason for a non-obvious exception rather than abandoning the required toolkit. Match the original behavior for evaluation order/count, eager versus lazy execution, short-circuiting/errors, borrowing/moves, allocation, output order, and duplicate-key handling. A Rust `HashMap` comprehension does not acquire Python dictionary insertion-order guarantees. Concise syntax cannot justify a changed invariant or hidden extra work.

Use rustfmt, relevant Clippy checks, rust-analyzer, and focused compile/runtime/property evidence for changed patterns. Add small compile-checked examples beside the reused pattern explaining the comprehension/template and any non-obvious Rust borrowing or error behavior for Python developers. Keep imports, naming, and template vocabulary consistent and searchable. Readability means lower learning/reasoning cost for both Python and Rust developers, not simply fewer characters; no separate style framework or repository-wide cosmetic rewrite.

## Appendix D — Implementation gate and property extraction

**D1 — Gate record and legal transitions.** Use orthogonal fields:

```text
stage = DISCOVERED | IMPLEMENTING | IMPLEMENTED | EXTRACTING |
        PROPERTIES_READY | VERIFYING | VERIFIED | DELIVERED
disposition = READY | BLOCKED | UNSUPPORTED | STALE | SUPERSEDED | EXCLUDED_BY_USER
```

A content-addressed implementation gate binds feature ID, baseline/scope revision, production paths/symbols and reachable application call path, tree/dirty-source digest, acceptance criteria, commands/results, and predecessor ledger revision. `IMPLEMENTED` means the complete selected feature exists and passes its implementation checks; it is not a formal-verification claim. The extractor consumes this gate plus explicit feature-to-source-test mappings and rejects absent/stale/unfinished gates. Stubs, hardcoded fixtures, incomplete halves renamed as milestones, and uncalled functions fail. A justified infrastructure/refactoring change has its own checks and bindings, but cannot be relabeled an Agones feature to front-load generalized machinery or extract unfinished production behavior. Build extraction support only for completed, gated features, starting with the smallest supported source-test family.

Defects reopen implementation and stale affected results. Source tests, helpers, rules, domains, or mappings changing require affected extraction to rerun; a production-only fix reuses unchanged extracted properties and reruns their proof/runtime checks. Preserve the gate-to-extraction event order using immutable snapshot/transition hashes even after squash merges. Unsupported/blocked/stale required items never count complete. Superseded items retain links to replacements; exclusions retain user authority.

**D2 — Package-aware loading and stable identity.** Prefer `golang.org/x/tools/go/packages` with tests and required syntax/type information, or an existing loader demonstrating equivalent semantics. Bind Go version, GOOS/GOARCH, build tags, module/replacement/vendor graph, cgo/generated sources, feature gates, and relevant non-secret environment. AST parsing alone does not resolve external test packages or assertion semantics. [Go packages documentation](https://pkg.go.dev/golang.org/x/tools/go/packages).

Use package + source path + top-level test + full subtest/case identity + assertion identity, linked to configuration ID and source blob/span/content binding. Explicit case keys are preferred; ordinals only disambiguate within a content binding and are not durable identity. Preserve duplicate names, aliases for moves, and tombstones. Compute fixture/helper/assertion-library closure; unresolved calls remain visible.

The extractor's support matrix must explicitly address table/subtest closure capture, `t.Helper`, `t.Cleanup`, `t.Parallel`, setup/teardown/global initialization, goroutines/channels, clocks/timers/eventual assertions, map order/randomness, testdata/embed, mocks/fakes, and network/process I/O. Mark unsupported semantic constructs; do not silently ignore them or substitute guessed outcomes. Classify tests as deterministic, bounded nondeterministic, environment-sensitive, or flaky/unknown. Preserve permitted outcome sets and source-supported timing assumptions.

**D3 — Typed property representation and fidelity.** Each declaration binds origin IDs, fixture/helper closure, Go domain/environment, Rust domain mapping, action sequence, observation projection, assertion relation, exceptions/errors, independent reference mapping if used, production entrypoint, assurance category, domain assumptions, bounds, covers, and transformation-rule IDs. “Identical invariants” means preservation of the original observable relation under the declared translation, not textual similarity or copying the implementation. Cover integer widths/overflow, nil/empty/omitted values, defaults, strings/enums, protobuf presence, pointer/identity semantics where observable, clocks/time zones, ownership, and async order.

Classify obligations as `EXACT_CASE`, `FINITE_TABLE_LIFT`, `SOURCE_CONTRACT_PROPERTY`, `DERIVED_PROPERTY`, or `MANUAL_ADDITIONAL_INVARIANT`. The first three can discharge original obligations only with traceability and a justified observation relation. Additional properties cannot replace original cases. Unsupported mappings remain unresolved, not an extra “passed” class. Concrete examples do not uniquely define a universal law; preserve them as mandatory witnesses while generalizing only with source-contract evidence.

Assert `P(input, reference_observation)` and `P(input, production_observation)` independently; differential agreement is additional evidence. Do not derive expected results from production code, have the reference call the algorithm being checked, or trust the reference without invariants. A translated Rust reference is not the Go program: preserve its mapping and require deterministic Go/Rust concrete replay for supported families. If execution is unavailable or inherently environment-dependent, record the exact gap and available substitute evidence without silently counting the missing required category as complete.

**D4 — Validate extraction and failures.** For new/changed semantic rules, use representative original witnesses, duplicated names, unsupported cases, source invalidation, and bounded negative controls detecting real boundary/sign/defaulting/order/missing-update faults. Isolate mutations in separate package identities/targets; never contaminate production artifacts. Reuse validated rule evidence while bindings match. Persist counterexamples with obligation/domain/source hashes, engine, seed or model values, replay command, and minimized input where meaningful. After repair, promote a distinct useful witness to a regression; avoid an unbounded committed random corpus.

## Appendix E — Formal evidence, reproducibility, and CI

**E1 — Shared domains and non-vacuity.** Define domains, preconditions, assertions, and required covers separately. Generate Bolero inputs and Kani symbolic inputs/assumptions from that declaration. Demonstrate equivalent accepted domains for each family; if they differ, retain separately named obligations and residual coverage. `TypeGenerator` and `kani::any` are not automatically equivalent. Track accepted/rejected input counts for filtered sampling. An early `return true` cannot substitute for valid-domain coverage.

Each credited mapping needs a valid-domain witness, reachable actual assertion/production path, and witnesses for semantically important outcomes/branches it claims. Use supported Kani covers/reachability results and inspect their status individually. An impossible cover requires source justification and correction of the claim; deleting it to obtain success is not a repair. Record adequate unwind checks, collection sizes, integer widths, event schedules, assumptions, stubs, and termination conditions. Smaller models may diagnose failures; they cannot silently discharge larger required claims. [Kani result semantics](https://model-checking.github.io/kani/verification-results.html).

**E2 — Backend and production connection.** Establish a real Bolero-to-Kani invocation for the selected versions; verify current help, discovery, and engine output. Retain exact replay commands, harness IDs, expected counts, and selected features. Include test-mode/dev-dependency handling where needed; direct Kani's `--tests` is one version-sensitive example, not a guessed flag to forward through every CLI. Keep reusable direct Kani harnesses, but label that route separately and avoid proving identical obligations twice without purpose. Separate generated harnesses alone do not establish the required backend route. [Bolero package documentation](https://docs.rs/bolero/latest/bolero/), [Kani usage](https://model-checking.github.io/kani/usage.html).

For every proof, record the exact verified symbol and real production call sites. A harness calling the actual pure production function can establish that function's bounded property; it does not certify the surrounding async controller. Model effects explicitly and validate production state extraction, ordering, persistence, error mapping, and cancellation with integration tests. Never replace production behavior under `cfg(kani)` and credit it as the same implementation. Record external/trusted boundaries for Rusternetes, OS, HTTP/TLS, Extism, native/FFI code, and unsupported concurrency. Deterministic sequential models of event interleavings are models, not proof of an executor's actual concurrent behavior.

**E3 — Reproducible dependency/evidence graph.** Commit a root application `Cargo.lock`, use locked resolution for evidence runs, and pin the exact evidence Rust toolchain independently of the minimum supported Rust version. Pin Bolero/cargo-bolero, Kani and its supplied compiler/backend/solver, Go, generator/rule tools, flags, targets, features, and native tools affecting output in a versioned manifest. Do not assume one Rust compiler serves every tool; validate compatible toolchain combinations. Dependency updates invalidate affected evidence and require reviewed refreshes.

Materialize a content-addressed DAG linking source test/helper/fixture/configuration nodes -> translation/mapping/rules/IR -> harness/generator -> production symbols and dependencies -> run/results/covers. Include file inventories so additions/deletions/renames and relevant vendored/submodule changes invalidate reuse. When a dependency closure is uncertain, invalidate conservatively instead of claiming a narrower cache hit. Record the full source snapshot plus relevant closure; a changed unrelated doc need not reprove an unaffected function. Label reused evidence and verify artifact availability.

**E4 — Assurance and gates.** Track source-mapped, harness-generated/compiled, sampled-property, reference-model-checked, production-symbol-model-checked, differential-replayed, and Rusternetes-integrated separately, with required IDs/counts per feature. All selected required harnesses/assertions/covers must be accounted for; nonzero total alone is insufficient. Parse exit status and complete individual results. Missing tools, timeouts, solver errors, unsupported operations, unsatisfied required covers, truncated logs, stale bindings, or unexpected empty selection are unavailable/inconclusive/failing states, never success.

Use cheap model diagnostics, required adequate bounded proofs, and explicitly scheduled deeper campaigns. Diagnose state explosion through dependencies/model structure and proven decomposition rather than arbitrary weakening. Deep work may be deferred to its scheduled stage so unrelated implementation progresses; required proof debt remains open and blocks final completion.

Add CI gates as their underlying feature/tooling is implemented, using already completed features to establish the first vertical slice. Required gates cover schema/scope consistency, exact lock/tool versions, reproducible generation, architecture boundaries, deterministic source replay, nonempty exact Bolero/Kani selections, Rusternetes conformance, and evidence freshness. A cheap always-run dependency/freshness job selects affected expensive jobs; if path filters exist, derive them from the same dependency manifest. Required checks must match the delivered commit. A skipped proof job is not replaced by a green Cargo test job.

## Appendix G — Token economics, periodic refactoring, and continuation

**G1 — Mandatory token/completion ROI gate.** A new macro or generalization MUST NOT be implemented unless evidence or strong deductive reasoning shows that implementing it now is expected to reduce total future AI token consumption or materially accelerate Agones-rs completion. If its expected construction cost exceeds the tokens it will save over the remaining migration, do not implement it; continue feature work directly within CGP. Elegance, hypothetical reuse, or “this may be useful later” is insufficient. Include implementation, integration, validation, maintenance, compiler/diagnostic costs, and future agent comprehension in the comparison. A mandatory final matrix cell cannot automatically justify any proposed implementation.

Before substantial macro/refactoring work, record a few sentences or one compact row using existing state, covering:

- Concrete existing repetitions and realistically expected remaining repetitions, with paths and active/near-future feature IDs.
- How often agents would otherwise regenerate/edit/explain the pattern and its production/property/harness plumbing.
- Expected reduction in handwritten boilerplate, mechanical inconsistencies, future reasoning, prompt/context reads, code-edit tokens/credits, verification-writing effort, and Python-to-Rust learning friction.
- Existing Agones, CGP, derive-deftly, comprende, better_comprehension, Arcane-rs, and Genco solutions and the smallest remaining gap.
- Estimated implementation/validation/maintenance burden and likely compile-time, generated-size, and diagnostic effects.
- The break-even argument, confidence, bounded work scope, success check, and stop/revisit condition.

Use rough ranges or a clear deductive argument, not fabricated exact token or credit savings. Include the cost of learning unfamiliar macro syntax, diagnosing expansions, and explaining patterns in future turns. Account for remaining work, not imaginary future projects. An immediately blocking capability can justify a minimal solution by a concrete completion argument, but does not authorize surrounding general infrastructure. Compare reuse, a small local refactor, and direct implementation before generalizing. Recheck the decision if scope/cost grows; stop expansion when the rationale no longer holds. No dedicated ROI database, benchmark suite, or accounting framework.

```text
positive, evidenced token/completion ROI -> implement the smallest useful change
uncertain or negative macro ROI          -> continue feature implementation
```

Optimize verified progress per total AI tokens + compute + maintenance effort subject to unchanged correctness, scope, architecture, verification quality, and recoverability. Choose dependency-closing Agones slices with useful parity gain. Budget implementation, extraction, fast checks, proofs, integration, and delivery without allowing framework construction or proof-depth exploration to consume all progress capacity. Keep required proof debt visible. Operational command limits are not invented Goal budgets. No identical deterministic retries; changed hypotheses justify new attempts, and transient failures use a bounded backoff policy with durable attempt records.

**G2 — Avoid repeated reasoning and work.** Use one compact work packet with active feature/requirement IDs, relevant source excerpts, content hashes, applicable instructions, settled decisions, and exact next action. Reuse source inventories, generated metadata, capability notes, and dependency closure; do not rescan the whole repository, reread full files or the whole prompt, revisit settled framework comparisons, regenerate unchanged output, or recompile/reprove fresh evidence without a reason. On hash/dependency changes, refresh only affected material; uncertain closure invalidates conservatively. Reuse never means trusting stale or missing results.

Use `rg` and bounded reads. Batch independent reads and shared setup; serialize overlapping edits/build/Git mutations. Cache with source/configuration/tool bindings. Measure representative clean/incremental compile cost, generated size, repetitive handwritten work removed, diagnostics/IDE behavior, and material CI/binary impact for consequential abstractions. Do not benchmark each small edit or produce repeated explanations of settled choices.

Checkpoint before long operations and yields: objective/contract/scope hashes, checkout/dirty paths, work kind and feature stage, gate/evidence refs, jobs/retries/blockers, `_2` matrix/refactoring decisions and next trigger, measured resource use where available, and exact next action. Preserve decisions/evidence, not private reasoning transcripts. No other chats, automations, or sub-agents unless the user or applicable instructions explicitly authorize them; when delegated, use non-overlapping ownership and bounded context.

**G3 — Mandatory periodic refactoring/readability stage.** After a meaningful implementation or delivery milestone, scan recently changed and nearby code within a bounded work packet. Closely related milestones may share a review, but schedule it no later than the next such milestone; review earlier when substantial repetition becomes visible. Record the last review and a concrete next milestone/trigger. This is part of ordinary execution, not an optional end-of-project cleanup or a request to schedule a background automation.

Examine repetitive CGP provider declarations, trait forwarding, derives, attribute metadata, API/resource plumbing, conversions, collection transformations, property/harness declarations, controller/reconciliation wiring, and error/telemetry/lifecycle plumbing. Compare these with patterns concretely expected in remaining work.
